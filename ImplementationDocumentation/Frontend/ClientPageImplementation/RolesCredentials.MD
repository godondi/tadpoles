## Normal Compose setup

1. `docker compose up -d database`
2. `docker compose run --rm database-migrate`
3. `docker compose run --rm database-demo-seed`
4. Opt in to simulated openings: `docker compose --profile simulation run --rm database-simulation-seed`
5. Enable both admission and the durable worker: `TRADING_SIMULATION_ENABLED=true TRADING_SIMULATION_WORKER_ENABLED=true docker compose up -d --build backend frontend`
6. Open the login page. Preview and confirm a simulated buy; follow its receipt to the booked fill, then sell from Portfolio.

The default deployment leaves simulation off. The opt-in seed opens USD 10,000, GBP 10,000 and INR 100,000 for each demo client using unique journaled setup references. It never replenishes spent balances on rerun. New self-registered clients receive configured zero-balance currency accounts after onboarding when simulation is enabled; there is no client funding endpoint.

The role seed preserves existing passwords and memberships. These passwords only apply if the corresponding users were created by the seed. It does not reset an existing account's password.

The application currently uses the repository's development database connection. Do not treat this as a hardened deployment with a separately provisioned least-privilege runtime role. The rejected automatic role-provisioning change is not included.

## Disposable browser review

Run `bash scripts/start-client-review.sh` (it builds both applications). It creates a separate PostgreSQL container with no shared volume, builds the backend and exposes both apps only on loopback. It does not read `.env`. It deliberately has no external quote provider; the synthetic order preview works independently of provider chart availability. `bash scripts/stop-client-review.sh` deletes only this disposable review stack and its test data. Use `bash scripts/start-client-review.sh --reuse` to rebuild the review apps while preserving their database. Use Compose with its persistent volume for a persistent local demonstration.

## Non-owner deployment option

For a hardened environment, have the database administrator provision a dedicated non-owner login with a managed secret. Apply `database/runtime-grants.sql` as the migration owner with `psql -v runtime_role=THE_EXISTING_ROLE -f database/runtime-grants.sql`. Set `TRADING_RUNTIME_DB_USER` and `TRADING_RUNTIME_DB_PASSWORD` through the deployment environment, then use `docker compose -f docker-compose.yml -f docker-compose.hardened.yml up -d --build backend`. The override refuses missing credentials. No password is supplied or generated by the grants script. Keep migration credentials separate. The disposable recovery test verifies the grant set with a temporary NOLOGIN role, including an application fill under that role and denied evidence rewrite/truncate/trigger changes.

## Reproducible verification

`bash scripts/test-role-workspaces.sh` runs all requested suites in disposable containers. After packaging the backend, `python3 scripts/test-client-recovery.py` rehearses backup/restore, admission shutdown with job draining, idempotent replay, repeated restart, migration reruns and runtime grants in its own disposable containers (loopback port 18082). It deletes those test containers on exit and never touches Compose volumes.
